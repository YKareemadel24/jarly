## 1. Executive Summary

**Release recommendation — NO-GO.** Saving Jar tracks one person’s goals, habits and manually recorded contributions on one device. It does not move bank funds. The ordinary Chrome release-build path created a jar, recorded a $20 deposit and a $5 withdrawal, and restored the $15 balance and both history rows after an orderly close and reopen. That result covers a successful path. Boundary and failure checks found cases where the ledger records the wrong amount or direction, success precedes a failed write, and the lock exposes private data.

**Confidence is high** in the no-go decision and the logged domain, controller and widget outcomes. Confidence in the frequency of physical gesture reentry, abrupt interruption outcomes and native platform behavior is limited. No signed native build, physical-device biometric/notification/file flow, OS backup or reinstall, force-kill or power-loss recovery, native assistive-technology session, cold offline browser launch, live advisory sweep, or large-history performance test was verified. Historical credential validity, privileges, use and publication beyond the checked refs remain unknown.

| 1 | An accepted amount can gain or lose a cent at the supported limit. Ordinary grouped paste can also become a different amount before confirmation. | A01, B01 |

A and B IDs come from the earlier passes. C01–C02 identify the two highest-priority Pass 3 security findings. ## 4. Findings by Severity

### P0

#### A01 — Accepted amounts can lose exact cents

- **Affected flow and confidence** — High. Target, deposit, withdrawal, recurring and correction entry. Pass 1’s native Dart probe observed the conversion and formatting error. The end-to-end large-value UI effect follows from the callers.
- **Observed and impact** — Parsing `90071992547409.01` produced `9007199254740902` minor units, one cent too many. In the near-maximum sweep, 33 of 92 accepted inputs converted incorrectly. Adjacent amounts could display identically. The correction editor round-trip can change the amount on a note-only edit. Exposure requires unusually large supported inputs. [Conversion](../lib/domain/money.dart#L25), [display](../lib/domain/money.dart#L69), [correction editor](../lib/ui/screens/jar_detail_screen.dart#L1925).
- **Expected behavior and fix** — Parse, format and round-trip accepted text with exact minor units. Use decimal digit parsing and integer quotient/remainder formatting. Audit preset and edit initializers that divide by 100. Keep the legacy numeric migration contract explicit.
- **Regression** — Test adjacent cents and both sides of the supported bound in preview, persistence and correction. A note-only edit must preserve the original amount.

### P1

#### A02 — Savings success precedes persistence and the failure alert can fail

- **Affected flow and confidence** — High. Create, edit, deposit, withdrawal, correction, Undo and restore. A failed-write probe observed success, in-memory balance 125 and persisted balance 100. B04’s alert failure follows from verified widget ancestry.
- **Observed and impact** — `_commit` publishes the new state before a queued write. It can also publish in read-only or pre-ready state, where `_schedulePersist` returns immediately. The adapter ignores a `false` preference setter result. Transaction feedback starts from the synchronous result. Closing after a failed or unfinished save can lose an acknowledged change. The warning has `Semantics` between `Stack` and `Positioned`, an invalid parent-data path that can prevent the failure alert from working. [Commit](../lib/state/savings_controller.dart#L148), [adapter](../lib/data/key_value_storage.dart#L44), [feedback](../lib/ui/screens/jar_detail_screen.dart#L146), [root stack](../lib/app.dart#L46), [banner](../lib/ui/widgets/storage_warning.dart#L18).
- **Expected behavior and fix** — Serialize validation and commit against the latest accepted snapshot. Reject unavailable/read-only mutations, propagate failed writes, and acknowledge only a successful commit. Keep retry safe for overlapping intents. Put `Positioned` outside the banner’s semantics wrapper. The locked SharedPreferences README explicitly disclaims guaranteed disk persistence after return. Use a storage mechanism with a defined durability guarantee for the ledger, preserve existing data during migration, and test interruption separately from awaiting the adapter.
- **Regression** — Block and fail a write, simulate a `false` setter, and render the actual app root. Assert pending/error feedback without success haptics, toast or celebration. Retry and reload to exactly one committed entry. Exercise an interrupted write and a later queued write.

#### A03 — Native storage failure looks like a fresh writable store

- **Affected flow and confidence** — High in the source path. Native preferences initialization failure was not induced on hardware. B08 identifies related loading/error presentation gaps.
- **Observed and impact** — `createStorage` catches native initialization failure and returns an empty `MemoryStorage`. The savings loader treats missing keys as an empty writable store and settings treat absent lock flags as disabled. New entries are volatile and configured lock protection can be skipped for that session. Home also renders a provider error as loading, while detail, Activity and Insights can show missing or empty data before hydration or after failure. [Fallback](../lib/data/key_value_storage.dart#L56), [load](../lib/data/savings_storage.dart#L74), [settings flags](../lib/state/settings_controller.dart#L134), [lock policy](../lib/lock/lock_policy.dart#L32), [Home](../lib/ui/screens/home_screen.dart#L39), [detail](../lib/ui/screens/jar_detail_screen.dart#L81), [Activity](../lib/ui/screens/activity_screen.dart#L35), [Insights](../lib/ui/screens/insights_screen.dart#L21).
- **Expected behavior and fix** — Report unavailable storage explicitly, block financial writes and keep the lock closed when policy cannot be read. Provide a recoverable error state and distinguish it from pending, genuinely empty and missing-ID states.
- **Regression** — Fail storage initialization and then retry against the original populated store. Assert no writable empty state, no unlocked app and no false missing-jar message.

#### A04 — One confirmation can record two financial mutations

- **Affected flow and confidence** — High for the two same-frame widget reproductions. Physical rapid-tap incidence is unverified.
- **Observed and impact** — The callback retains the build-time amount and reads mutable direction. The first success clears the direction. Reinvoking the same callback duplicates a deposit or makes the second withdrawal callback a deposit. A separate draft problem, B06, allows a dismissed deposit’s amount and note to prefill a later withdrawal. [Captured amount and direction](../lib/ui/screens/jar_detail_screen.dart#L110), [record callback](../lib/ui/screens/jar_detail_screen.dart#L129), [direction reset](../lib/ui/screens/jar_detail_screen.dart#L179), [dismissal](../lib/ui/screens/jar_detail_screen.dart#L403).
- **Expected behavior and fix** — Capture a fixed amount and direction, consume the intent synchronously before awaiting the commit, and clear the draft on cancel. A handled failure can reopen the same intent for a safe retry.
- **Regression** — Invoke the same rendered action twice for both directions and reload. Assert one correctly signed entry, one acknowledgement and a clean opposite-direction form after cancellation. Also check real rapid taps.

#### A05 — Recurring execution can replay, skip or add unintended entries

- **Affected flow and confidence** — High. Pass 1’s controller probe observed the unsaved catch-up. The lifecycle, archive, malformed cadence and editor paths are confirmed in source. Includes A15, B03 and B05.
- **Observed and impact** — Startup publishes catch-up without saving its entries or cursor. In the probe a due contribution displayed 25 while storage remained at 0. Reopening from the old cursor re-creates the occurrence until a later save captures it. Resume only resyncs notifications. The runner processes an archived jar before checking its flag. A malformed stored cadence passes hydration and can apply one due occurrence up to 366 times if balance limits permit because the cursor never advances. The editor starts with a weekly draft and fails to hydrate the saved cadence on open. [Hydration](../lib/state/savings_controller.dart#L199), [resume](../lib/ui/widgets/notification_resync.dart#L35), [rule validation](../lib/data/savings_storage.dart#L68), [cadence fallback](../lib/domain/schedule.dart#L34), [catch-up](../lib/domain/schedule.dart#L63), [archive order](../lib/domain/schedule.dart#L89), [editor draft](../lib/ui/screens/jar_detail_screen.dart#L53), [editor open](../lib/ui/screens/jar_detail_screen.dart#L884).
- **Expected behavior and fix** — Persist due entries and cursor together on startup and resume through A02’s commit path. Validate cadence and due date before execution, stop a nonadvancing cursor, and hydrate the editor from the stored rule. Treat archive as a pause and resume the rule from restore time without backfilling the archived interval. This is the proposed archive policy.
- **Regression** — Reload, resume twice and reload again with the same store and clock. Assert stable occurrence IDs, correct balance and cursor, no entries for paused/archived/malformed rules, and preserved cadence after amount-only edits.

#### A06 — Lock settings can report protection or leave an unusable lock

- **Affected flow and confidence** — High. Pass 1 fault injection observed biometric enable reverting on restart and failed PIN disable restarting with the lock flag enabled and no credential.
- **Observed and impact** — Best-effort writes swallow failures and publish state first. PIN disable removes the credential before saving the disabled flag. A user may believe lock is active when it will reopen disabled, or lose access to a PIN-only store. Similar write handling can revert currency, appearance and reminder preferences on restart (B09). [Lock preference writes](../lib/state/settings_controller.dart#L158), [PIN disable](../lib/state/settings_controller.dart#L206), [appearance](../lib/state/providers.dart#L70), [currency](../lib/state/settings_controller.dart#L263).
- **Expected behavior and fix** — Await and report writes that change protection. Enable only with a usable persisted credential. Save the disabled policy before credential cleanup, retain a usable credential if that write fails, and reconcile UI settings with persisted state.
- **Regression** — Fail each credential and flag operation independently, recreate settings against the same storage and verify both access and the displayed lock policy. Test ordinary preference failure and retry too.

#### A07 — Android’s activity cannot host the configured biometric prompt

- **Affected flow and confidence** — High in the host and pinned plugin contract. Device lockout remains inferred.
- **Observed and impact** — `MainActivity` extends `FlutterActivity`. Locked `local_auth_android` 2.3.0 rejects authentication on an activity that is not a `FragmentActivity`. The app can detect enrolled biometrics independently and maps a prompt exception to `false`. A biometric-only configuration can leave the gate with no working unlock method. [Activity](../android/app/src/main/kotlin/com/app/savingjar/jarly/MainActivity.kt#L5), [plugin lock entry](../pubspec.lock#L528), [capability](../lib/state/settings_controller.dart#L109), [auth call](../lib/state/settings_controller.dart#L269), [gate](../lib/ui/screens/lock_gate.dart#L81).
- **Expected behavior and fix** — Use `FlutterFragmentActivity`, check the plugin’s applicable theme requirements, and verify successful authentication before enabling biometric-only protection.
- **Regression** — On Android with enrolled biometrics, enable the lock, background/foreground, unlock, and test cancellation, PIN fallback and recovery.

#### A08 — Import, restore and hydration disagree about valid balances

- **Affected flow and confidence** — High. Pass 1 observed native transfer/backup accepting unsafe target and recurring values, and a restore followed by rollback on reload. The contradictory local ledger case from B02 follows from the checked validators. Includes A13’s aggregate subcases.
- **Observed and impact** — The wire integer predicate accepts any native `int`, while hydration checks target and recurring amounts against the safe bound. The transfer merge replays ledger history, while local hydration checks entry shape and audit links without replay. A snapshot can therefore present a balance that disagrees with explicit opening balance and history, or be saved by import and rejected on the next launch. At the safe total boundary, restore skips the aggregate guard and catch-up uses only the running prefix of the active list. A reload can fall back to older data. [Wire money](../lib/transfer/transfer.dart#L294), [merge](../lib/transfer/merge.dart#L107), [hydration](../lib/data/savings_storage.dart#L40), [stored jar checks](../lib/data/savings_storage.dart#L51), [ledger replay](../lib/domain/transactions.dart#L103), [restore](../lib/state/savings_controller.dart#L298), [catch-up total](../lib/domain/schedule.dart#L89).
- **Expected behavior and fix** — Apply safe bounds consistently to incoming numbers and use shared ledger invariants at load and before commit. Preserve legacy opening balances. Check restore and catch-up deltas against the full starting active total, independent of order. Keep the transfer frame format and existing compatibility limits.
- **Regression** — Exercise native and web numeric boundaries, contradictory and legacy ledger fixtures, both jar orders, and restore at the aggregate limit. Assert that invalid operations leave current and backup data usable and valid operations reload identically.

#### A09 — A supported deadline can block full backup

- **Affected flow and confidence** — High. Pass 1 observed a `December 2026` deadline accepted by the domain but rejected on transfer decode and file creation. B07’s invalid create/edit mismatch follows from source.
- **Observed and impact** — The domain accepts month/year text. Transfer uses the stricter timestamp parser for the deadline field. A single supported deadline can invalidate the whole store’s export. Create also accepts arbitrary deadline text that Edit later refuses to save even during a name-only change. [Create](../lib/ui/screens/new_jar_screen.dart#L79), [edit validation](../lib/ui/screens/jar_detail_screen.dart#L277), [domain parser](../lib/domain/insights.dart#L80), [wire deadline](../lib/transfer/transfer.dart#L334), [backup self-validation](../lib/transfer/backup.dart#L124).
- **Expected behavior and fix** — Use one optional-deadline policy for create, edit and transfer. Read existing friendly dates and keep the wire field and bound. Preserve strict timestamp validation for actual timestamps. Provide an edit/recovery path for already-saved invalid dates.
- **Regression** — Round-trip ISO date-only, timestamp and Month Year values through local load, QR and `.jarly`. Confirm invalid text is handled explicitly and repairable in existing jars.

#### A10 — Android build configuration misses pinned notification requirements

- **Affected flow and confidence** — High in the configuration mismatch. Its effect during Gradle compilation is inferred because both APK attempts stopped at missing Java.
- **Observed and impact** — The app inherits Flutter’s compile SDK 36 and does not enable or declare core library desugaring. The installed `flutter_local_notifications` 23.0.0 README requires a consumer compile SDK of at least 37 and desugaring. Android release also selects the debug signing config. A distributable Android build and its merged manifest remain unverified. [Android Gradle](../android/app/build.gradle.kts#L9), [compile options](../android/app/build.gradle.kts#L12), [signing](../android/app/build.gradle.kts#L32), [plugin pin](../pubspec.lock#L257).
- **Expected behavior and fix** — Provision the JDK/SDK, meet the pinned plugin’s SDK/desugaring contract, and configure release signing with private values kept outside source control.
- **Regression** — Build Android debug and signed release artifacts, inspect the merged release manifest, install on supported devices and verify notification scheduling and delivery.

#### A11 — Core controls block keyboard operation and scaled layouts

- **Affected flow and confidence** — High for widget probes and sampled contrast calculations. Hardware accessibility behavior remains unverified.
- **Observed and impact** — Tab, Enter and Space produced zero activations on the shared control, while tapping produced one. Core deposit, withdrawal and confirmation use it. The wizard has a separate gesture-only control. At 200% text, Pass 3 observed overflows in narrow tab and Withdraw rows and in populated Insights layouts. Some essential text missed the normal-text contrast threshold. [Shared control](../lib/ui/widgets/pressable.dart#L34), [wizard control](../lib/ui/screens/new_jar_screen.dart#L716), [detail actions](../lib/ui/screens/jar_detail_screen.dart#L665), [confirmation](../lib/ui/screens/jar_detail_screen.dart#L1403), [tab layout](../lib/ui/screens/tab_shell.dart#L62), [chart](../lib/ui/screens/insights_screen.dart#L624).
- **Expected behavior and fix** — Provide focusable controls with visible focus, standard keyboard activation and accurate semantics. Allow core rows to wrap or reflow and correct failing text colors. Apply the same behavior to shared and wizard controls.
- **Regression** — Complete create/deposit/withdraw with keyboard only, test semantic actions and modal focus, and recheck key screens at 200% text in both palettes on supported devices.

#### B01 — Pasted amount text can silently change meaning

- **Affected flow and confidence** — High in source. The exact transformation is derived from the sanitizer. End-to-end paste was not exercised in the browser.
- **Observed and impact** — The sanitizer turns the first comma into a decimal point, removes further separators and clips fractional digits. Pasting `1,234.56` produces `1.23`. A minus sign is stripped. Create and detail accept the resulting text as a valid amount. This is an input interpretation error at ordinary values. A01 is a distinct exact-cent conversion error after accepting a number. [Sanitizer](../lib/domain/money.dart#L75), [wizard formatter](../lib/ui/screens/new_jar_screen.dart#L740), [detail formatter](../lib/ui/screens/jar_detail_screen.dart#L1050).
- **Expected behavior and fix** — Define one money-entry grammar. Parse valid grouped input unambiguously and reject unsupported or signed values with guidance. Keep the preview tied to the exact accepted amount.
- **Regression** — Paste grouped, comma-decimal, ambiguous, signed and excessive-precision values into each amount editor. Assert either an exact value or an explicit rejection.

#### C01 — A credential was recorded in local Git history

- **Affected flow and confidence** — High for the presence and locations of a GitHub credential-pattern match. Validity, privileges and publication through any other ref or remote are unknown.
- **Observed and impact** — Pass 4 reconfirmed matches at `.codex/config.toml:5` in three historical local objects reported in Pass 3. Each failed the ancestry check against both reviewed `HEAD` and the locally recorded `origin/master`. A still-active credential could grant access within its permissions. [Location-only evidence](pass-3.md#confirmed-vulnerabilities-and-disclosures).
- **Expected behavior and fix** — Have the credential owner revoke or rotate it immediately and review its use. Move credentials to an environment-backed configuration. Assess any other copies with the owner after revocation.
- **Validation** — Confirm revocation and review usage through the owner’s account. Run a redacted scan of refs intended for distribution. Keep secret values out of evidence and logs.

#### C02 — The locked app exposes savings through Flutter semantics

- **Affected flow and confidence** — High. Pass 3 mounted the production root with a funded synthetic jar and an enabled PIN gate. Hardware screen-reader behavior is unverified.
- **Observed and impact** — The router remains mounted under a visible lock overlay. Its Flutter semantics tree still contains the jar name, percentage, saved amount and target. This exposes private ledger information on a surface intended to require authentication. [Root stack](../lib/app.dart#L44), [lock overlay](../lib/ui/screens/lock_gate.dart#L241), [jar label](../lib/ui/screens/home_screen.dart#L646).
- **Expected behavior and fix** — Exclude private route semantics, focus and interaction whenever the gate is locked or settings are unresolved. Restore route focus after unlock.
- **Regression** — With a populated store, assert private content and actions are absent while locked at launch and resume. Verify the unlock flow and focus on VoiceOver and TalkBack.

### P2

#### A12 — Android system restore can leave an unusable PIN lock

- **Affected flow and confidence** — Medium. Host configuration and secure-read handling are verified. The Android OS/OEM restore result is inferred.
- **Observed and impact** — The main manifest leaves backup and extraction policy at platform defaults. If a restore preserves the enabled preference and restores secure-store ciphertext without its original wrapping key, the secure read can return null and the gate remains closed. Device-local expectations also need an explicit cloud backup policy. [Manifest](../android/app/src/main/AndroidManifest.xml#L4), [secure read](../lib/data/settings_repository.dart#L141), [gate](../lib/ui/screens/lock_gate.dart#L524).
- **Expected behavior and fix** — Define cloud backup and device-transfer rules. Exclude device-bound credentials and ensure the restored lock flag has a deliberate, authenticated recovery policy. Keep the user-controlled file backup contract explicit.
- **Regression** — Restore an Android PIN-only installation with synthetic jars to a second device. Verify the intended data policy and usable access without weakening authentication.

#### A14 — Jar and sheet actions can lose the intended target or draft

- **Affected flow and confidence** — High. Pass 1 reproduced the delete no-op and Pass 3 reproduced system Back popping the detail route with a deposit sheet open. A16’s edit-cancel mutation follows from source.
- **Observed and impact** — `ActionSheet` dismisses before the Delete callback reads `_pendingDelete`. Dismissal clears the selection, so the jar and history remain. Selecting Goal/Habit writes immediately even if the user cancels the edit. The deposit sheet is a route-local overlay, so system Back popped the whole detail route in the probe. [Dismiss ordering](../lib/ui/widgets/action_sheet.dart#L86), [delete action](../lib/ui/screens/profile_screen.dart#L488), [kind edit](../lib/ui/screens/jar_detail_screen.dart#L446), [sheet overlay](../lib/ui/widgets/sheet_scaffold.dart#L74).
- **Expected behavior and fix** — Capture the selected jar ID before dismissal and acknowledge deletion after commit. Define how deletion interacts with the rolling recovery copy before promising permanent removal. Stage Kind with the rest of the edit. Close the active sheet before popping its route and make wizard Back respect steps.
- **Regression** — Verify confirm, cancel, backdrop and Back, then reload to confirm the intended mutations. Include the actual Android predictive Back and iOS gesture paths.

#### A17 — Notes, streaks and progress cues can disagree with the ledger

- **Affected flow and confidence** — High. Pass 1 observed note clearing, last-deposit/streak, rounded completion and fractional preset cases. Stale streak display and its label follow from source. Includes A18 and B11.
- **Observed and impact** — A null note or last-deposit value means “keep” in `copyWith`. Clearing a note retains it while adding a revision. Undoing the last habit deposit leaves its old date, and a same-day redeposit can leave streak at zero. Stored streaks can stay visible after inactivity, and Insights calls the maximum stored current counter “best streak.” At 99.5% Home and Insights mark a jar complete, while funded-only checks still require the exact target. A “Hit 25%” preset for a 101-minor target offers 25, one short, and can reoffer an already hit level after withdrawal. [Nullable note](../lib/domain/jar.dart#L209), [last-deposit field](../lib/domain/jar.dart#L393), [recompute](../lib/domain/transactions.dart#L98), [streak update](../lib/domain/jar.dart#L561), [Home completion](../lib/ui/screens/home_screen.dart#L58), [Insights metrics](../lib/ui/screens/insights_screen.dart#L28), [preset](../lib/domain/presets.dart#L75), [milestones](../lib/domain/jar.dart#L502).
- **Expected behavior and fix** — Make explicit field clearing possible while preserving revisions. Derive the current streak against the local day and label the metric accordingly. Use exact balance/target for completion and the same ceiling rule and hit-level data for presets and milestones.
- **Regression** — Verify cleared notes and revisions after reload, Undo and same-day redeposit, an expired streak, balances around completion, fractional milestone targets, and withdrawal/redeposit without a second award.

#### A19 — Notification timing, permission and recovery vary by platform

- **Affected flow and confidence** — High in the source and pinned plugin contracts. OS prompts, deliveries and timezone-change effects remain unverified.
- **Observed and impact** — On Windows resync cancels reminders before scheduling today’s 09:00. After 09:00 the locked plugin rejects the past date and later jar schedules are skipped. Windows’ time-component option schedules only one occurrence. On iOS initialization runs before the enabled check, with default alert, sound and badge permission flags enabled. The app can request permission before opt-in. The timezone lookup runs once per process, so foreground resync can retain stale zone rules after travel. [iOS initialization](../lib/services/notification_service.dart#L26), [zone cache](../lib/services/notification_service.dart#L122), [rebuild order](../lib/services/notification_service.dart#L139), [daily schedule](../lib/services/notification_service.dart#L157), [error handling](../lib/services/notification_service.dart#L219).
- **Expected behavior and fix** — Start Windows at the next future check-in, use supported replenishment behavior and preserve per-jar delivery when one request fails. Set iOS initialization permission flags to false and keep the explicit Profile opt-in. Refresh timezone data before rescheduling after a zone change.
- **Regression** — Test scheduler calls around 09:00, disabled initialization and a simulated zone change. On hardware verify permission denial and retry, next-day delivery and foreground after travel.

#### A20 — Transfer disclosure and native file bounds are incomplete

- **Affected flow and confidence** — High in source. The consequences of sharing the payload or allocating a very large file are inferred. Includes Pass 3’s transfer privacy finding.
- **Observed and impact** — The device transfer UI counts active jars, but the common exporter encodes the entire list including archived histories. The mismatch can say there are no jars while producing shareable records. The native picker accepts any file and allocates the whole content before the 512 KiB limit is applied. An oversized selection can exhaust memory. [Hub count](../lib/ui/screens/transfer_hub_screen.dart#L31), [Send snapshot](../lib/ui/screens/transfer_send_screen.dart#L40), [Send count](../lib/ui/screens/transfer_send_screen.dart#L75), [exporter](../lib/state/savings_controller.dart#L353), [native read](../lib/services/backup_io_native.dart#L27), [size limit](../lib/transfer/backup.dart#L14).
- **Expected behavior and fix** — Show the exact export scope, including archived history, before displaying or sharing device codes. Keep documented full-history file backup. Bound native reads before full allocation and cap the read in case the file grows. Correct sharing and camera wording to match local-copy and paste behavior.
- **Regression** — Compare disclosure to decoded contents for active, mixed and archived-only stores. Test a file over the limit and one that grows during read. Check non-ASCII jar names through native file I/O.

#### B10 — Delayed UI feedback can outlive its original action

- **Affected flow and confidence** — High in source. Timing and disposed-widget outcomes are inferred. Includes B12.
- **Observed and impact** — A replacement Undo toast inherits an earlier timer when the visible flag stays true. A pending timer can also dismiss a later toast after a hide/show sequence. Eligible Undo remains in history. Profile and backup completions can call `setState` after awaiting a platform result or handling its error when the route has already been disposed. - **Regression** — Replace a toast near expiry and assert the new one gets its full interval. Dispose Profile or backup while an operation is pending, then complete and fail it separately without a widget exception.

## 11. Final Verdict

**NO-GO for release.** The normal web workflow is functional and the core layers are maintainable. The confirmed ledger and lock failures are release blockers.

| Question | Answer |
| --- | --- |
| Is the core saving flow trustworthy? | **No.** The normal web flow passed, but accepted amounts, repeated confirmation and commit feedback can disagree with the user’s intent or saved state. |
| Can financial state become inconsistent? | **Yes.** Duplicate or wrong-direction entries, contradictory stored history, recurring replay and invalid restored totals are supported by probes or verified code paths. |
| Is persistence reliable? | **No.** Orderly web restart worked. Failed writes can be acknowledged, unavailable native storage can look writable, and the rolling copy can restore an older state. Crash durability is unverified. |
| Is the app accessible enough for release? | **No.** Core keyboard activation fails, critical layouts overflow at 200% text, sampled text contrast fails and the lock leaks private semantics. |
| Is the architecture maintainable? | **Yes, with targeted boundary changes.** Pure domain functions, provider injection and a centralized savings controller give clear repair points. Commit timing, duplicated validation and route-local modal state are the main liabilities. |

**Three next engineering actions**

1. Revoke or rotate the historical credential, close the locked semantics/focus surface and make lock transitions recoverable.
2. Fix exact amount entry and one-intent submission, then make ledger validation, durable commit and user feedback agree across manual mutations, recurring runs and restore.
3. Put the core keyboard and 200%-text flows and signed native build/device checks behind a release gate. Include interrupted writes, biometrics and notifications in that gate.
